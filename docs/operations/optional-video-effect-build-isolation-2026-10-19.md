# Optional video effects and unrelated releases

Build preparation assesses Hotel Lobby and Raindance separately for each 5- and 10-second option. A known refusal from the same template/price resolver used by new orders records `available: false` and its fixed source-defined reason code. The automatic Git build prints this assessment with its effect-price preflight. Missing, unconfirmed, invalid cost settings and expired effect approvals do not prevent unrelated fixes from being built.

This assessment never edits the enabled flags, packed policy, prices, approval dates or credentials. It does not grant admission. The existing capability endpoint returns `available: false` with the public `TEMPLATE_UNAVAILABLE` reason when new-order admission fails. Upload, quotation and first job creation still use the actual runtime template, price, safety, credit and binding checks. No new production configuration is required by this change.

Malformed packed JSON, flat/packed conflicts, invalid explicit override transport, ordinary-video readiness and pricing failures, required global authentication/database/storage settings and unknown exceptions still stop preparation. Unknown resolver exceptions use a fixed fatal diagnostic without exposing their arbitrary error text. The existing approved effect-price/markup totals are now a shared new-admission assertion for Hotel Lobby and Raindance at 5/10 seconds under the existing retail approval version. Standard/annual credit counts remain 69/69 and 116/101, with the same approved markups. Price or markup drift makes that optional capability unavailable and rejects new uploads, quotes and jobs before any ledger mutation. Rumpelstiltskin and legacy non-retail pricing are outside this assertion; no effective price is renewed or changed.

Accepted-order replay checks persisted admissions before current price checks. Existing state/history/playback read the owner-scoped order and frozen template snapshot; playback additionally requires settled funding and approved output. Recovery retains its existing safety and emergency runtime gates. Keeping all feature flags and policy bytes intact avoids turning this build change into a new kill switch for accepted work.

Verification uses synthetic policies, mocked database transports and local preparation. It does not certify current production policy, a live external payment/model request or a live production deployment. No migration or policy renewal is included.
