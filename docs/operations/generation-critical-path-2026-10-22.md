# 生成关键路径压缩（2026-10-22）

范围：图片、普通视频和模板涉及的上传、提交、执行、审核、存储、结果读取与播放。目标是减少模型运行之外的真实等待；不调整页面布局、样式、文案或价格。本轮为本地代码和验证，未推送、部署、修改生产配置或调用真实付费模型。

## 判断依据

每项操作必须回答：它是否取得此前没有的必要事实，是否维护不可替代的状态不变量，是否必须阻塞下一步？对同一不可变内容重复读取、重复授权投影、重复创建调度实例，不因为已有实现而保留。权限、完整解码、内容审核、配额、扣费、任务身份和故障恢复仍属于必要工作。

参考项目 `D:/AIProject/Gefei/SaaSTool/shipany-agent-temp/shipany-video-agent` 的 `src/modules/ai-tasks/video.ts` 在回调后查询供应商并等待 R2 转存，随后才写成功状态。页面每五秒查询数据库，速度并非来自更密的前端轮询。它使用公开 R2 地址，且不具备本项目相同的视频输出审核和私有交付约束；不能直接复制这些前提。

## 实际删除的工作

| 环节                             | 原路径                                                 | 新路径与边界                                                                                                                         |
| -------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 普通 JPEG/PNG 参考图封存后的校验 | 尺寸和完整解码各 GET 一次                              | 同一次有界读取完成两个检查：2 GET → 1 GET                                                                                            |
| WebP/模板参考图归一化            | API 前后检查及 storage 检查累计 5 GET + 1 HEAD + 1 PUT | 同一源字节检查、转换、内存中验证，再条件 PUT：正常路径 1 GET + 1 PUT；竞争时读取并验证实际 winner                                    |
| 模板场景图 fresh 写入            | 2 HEAD + 4 GET + 1 PUT                                 | recovery GET（通常 404）+ conditional PUT；供应商源图 GET 两边均保留。重新读取自己刚写入的场景图已删除                               |
| 模板场景图 replay                | HEAD + 3 GET                                           | 一次读取实际不可变 winner，同时计算校验和、检查尺寸并完整解码                                                                        |
| 图片输出类型识别与下载           | 供应商 GET 读取前缀并关闭，再 GET 下载                 | 同一经过主机/DNS/重定向策略校验的流识别类型并继续转存；未知大小、大文件和游客 staging 后备路径继续消费同一流                         |
| 图片连续阶段调度                 | 控制任务为每个 Outbox 事件创建子 Workflow 并查询状态   | 原 Workflow 领取确切事件，不再逐阶段新建 Workflow；普通控制与已知长度 URL 图片转存使用独立服务请求，取消全局四槽与普通图单槽限制     |
| 同步完成的图片审核               | POST 已包含完整结果，仍另发 retrieve                   | 先绑定审核任务和有效租约，再消费同一次认证 POST 的完整结果；任务/规则不匹配不放行                                                    |
| 异步图片审核                     | 完成后等待下一个查询间隔                               | 可验证回调仅推进同一任务的查询时间并唤醒认证查询；丢回调、未配签名密钥或唤醒失败仍有原轮询和恢复                                     |
| 普通视频提交                     | 浏览器 quote、create 两次串行请求，两个事务            | 一次 submit 请求、一个事务冻结 quote、job、积分预留与 VideoExecution；输入查询和锁复用，账户锁后的资格复验保留                       |
| 视频转存后的两次完整检查         | 审核前和交付前各下载整个 MP4                           | 转存完整检查的可信凭据绑定资产、对象、ETag、SHA256、字节数和冻结约束；两次后续检查仅各读 1 字节。旧任务、缺失/不匹配凭据继续完整检查 |
| READY → 播放授权                 | 状态请求后再请求 playback，并重新读取授权关系          | 状态响应复用同次新鲜、owner-scoped 授权投影生成短期播放凭证；旧缓存和过期凭证保留 playback 回退                                      |
| 视频 GET/Range 播放              | HEAD 后再 GET                                          | 一个 If-Match 条件 GET，核验 ETag、MIME、长度及范围；显式 HEAD 请求仍按原约束处理                                                    |

上传计数从素材已经封存之后开始，不含浏览器上传、seal/promote、数据库提交、清理及供应商审核。表中请求数量来自源码与测试断言，不是公网耗时测量。一次 Prisma 投影可能产生多条 SQL，不能把“一次查询函数”宣传为“一条 SQL”。

## 保留的正确性条件

- PostgreSQL 是业务事实来源。job、输入绑定、积分预留和持久执行意图仍原子提交；不可变账本继续使用稳定引用键。
- 图片、普通视频、模板场景的正常供应商提交不再获取 `media:provider-capacity:*` 全局独占锁：旧项目并发上限已退休，当前 claim 不维护跨任务容量计数。每 job/attempt 的防重与 may-have-sent 标记、owner 存储预留、素材身份、资金和预算锁均保留；未知受理不能重提。旧占用计数和锁只保留为明确命名的历史诊断，不导出为正常提交授权。
- 普通视频 v2 intent 在发请求前按账号写入浏览器存储；未知结果重试同一 key 和请求。请求内容或同意的价格不同产生冲突，已接受请求先于现行准入条件重放。重载或未知响应后，即使下一次请求收到模型退休、价格或余额拒绝，也不丢弃原 key：该拒绝无法证明之前仍在途的请求没有提交。价格变化明确返回 `quote_only` 后才解除未知状态，沿用现有确认操作。v1 确认回执和已接受历史模型继续可恢复，旧协议的恢复规则未整体重构。
- 新 Workflow 回执绑定事件、执行者及 lease token。真正完成后才 ACK；PENDING 保留同一审核任务与回执。执行前续租覆盖任务超时；过期 token 不执行。已 PROCESSED 但丢失响应时只重建后继状态，不再次执行付费提交。详见 [Workflow 协议](./image-workflow-continuation-2026-10-22.md)。
- 后续并发改造取消正常控制路径的全局 4 槽，以及普通已知长度 URL 图片转存的全局 1 槽。转存边读边验证边条件写入，遵守现有 25 MiB 图片大小上限；游客变换、内联数据、未知长度和旧 multipart 仍用受资源保护的路径。独立服务或 DO 名称不代表独立内存隔离；完整 50 用户的实测另报。
- 图片回调使用用途隔离的 HMAC 绑定资产、审核代次和 submission token，并验证 SeeAPI 原始请求体签名。回调体中的状态、task ID、URL 不作为业务证据。后续一秒预算实施把首个有效通知持久记录到当前代次：早到或活跃租约返回 202，不抢占租约；PENDING 提交保留查询期间新到通知的立即重查意图。
- 输出仍保留私有 MediaAsset、完整初次内容检查、SeeAPI/Waffo 审核、不可变对象条件写与资源上限。转存失败、未知供应商受理、错误租约、删除和过期都不能借优化变为成功。
- 同流转存不绕过 URL/DNS/重定向校验，不信任文件扩展名。所有成功、失败、提前返回均关闭持有的流；条件写冲突验证实际 winner，不能将本次未写入的字节身份冒充最终对象。

## 发布和回滚

最初的关键路径改造没有数据库 schema 迁移；后续一秒预算实施新增 `20261021173309_image_moderation_callback_wake`，须先应用 nullable 字段迁移。先部署兼容接收端，再上线新生产者；hybrid 必须先升级 Node 接收端再升级 Workflow。通知生产者由默认关闭的 `MEDIA_JOB_EVENTS_ENABLED` 控制，接收端和 DO 绑定就绪、旧消费者排空后才能启用。保留旧事件种类和无新回执的旧协议，直至已接受任务排空。回滚先停止新生产者，不能先卸载仍被持久 Workflow 使用的新回执接收器。

图片审核回调复用现有 `WORKFLOWS_DISPATCH_SECRET`、`NEXT_PUBLIC_SAAS_URL`，还要求有效的 `SEEAPI_WEBHOOK_SIGNING_KEYS`。本地环境文件未提供后者，不能据此声称生产已经获得回调加速；未配齐时同步结果优化仍生效，异步审核继续轮询。生产密钥、供应商回调送达、云端网络和实际用户延迟尚需获准后单独验收。

保留的时间来自模型和审核服务本身、必要网络传输、有效配额下的真实排队、事务一致性与异常恢复。进一步决定是否改动这些路径，应依据部署后的阶段时间；本次不宣称数学意义上的最短用时或线上功能已验收。
