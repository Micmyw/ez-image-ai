# Guest reference review and retry

The guest upload completion path previously converted every missing current approval into `GUEST_UPLOAD_NOT_READY`, including quarantined and failed assets. The public procedure returned `PENDING` for that error. After bounded polling, the browser reported a generic upload timeout and a manual retry allocated a new upload intent.

Completion now distinguishes a current, exactly bound content rejection, a current manual-review decision, and verification failure/untrusted evidence. These outcomes stop automatic polling and project separate safe messages. Only a genuinely uploading or verifying asset remains pending. Content, checksum, provider task, attempt/generation, rule, policy and evidence lifetime must match before the interface calls the result a content rejection or manual-review decision. Service errors and stale evidence cannot be presented as a content violation.

The existing current-approved authorization is still required before consuming the one-use completion token or creating a draft/bootstrap. Review/failure paths create no draft, release no hold, modify no moderation rule, and do not admit a generation after a timeout. Deleted or expired assets are rejected.

The mounted composer retains an acknowledged upload intent in memory. Its fingerprint binds the content SHA-256, size/type, capability version, product/SKU, prompt and image controls. An unchanged retry reuses the same session, asset, completion token and staged upload; after a successful PUT it only rechecks completion. The server still checks the original secret, origin, content hash, expiry and unconsumed state. A changed or expired checkpoint cannot be silently reused. Selecting a new reference or changing the requested content starts a new explicit action. No checkpoint/token is persisted in browser storage.

An intent whose creation response was lost cannot be recovered because its identity is unknown. Likewise, if a one-use claim was consumed and the complete success response was lost, the original claim secret cannot be reconstructed. An acknowledged checkpoint remains an unconfirmed request and is never silently replaced with another intent or declared successful. This change intentionally adds no credentials, HMAC claim protocol or token rotation. A known successful handoff can replay from the mounted composer's memory.

Regression tests cover terminal/current/stale evidence, genuine pending, unchanged approval, deleted/expired sessions and assets, secret/origin/content constraints, unknown responses, immutable input changes, completion replay, retry without another upload intent/PUT, and the distinct frontend messages. Database transaction tests inject the explicit database boundary, not a generated Prisma replacement. Full generated-client integration/type-check remains separately blocked by the official locked engine download policy; local focused tests do not imply production verification or deployment.
