## Advertising implementation and current blockers

Advertising is a partial delivery: isolation preparation and the disabled release path are complete, but the user's requested working, isolated placements have not been enabled or certified. The news and category can be released independently. The next approval and evidence requirements below remain open.

`BLOG_ADS_ENABLED` and `BLOG_NATIVE_ADS_ENABLED` both default to false. Do not activate them for this release. The first supplied snippet explicitly sets an iframe banner to 728 × 90. The second supplied hash/container is preserved as a separately gated widget, but its actual inventory has not been observed.

The parent supplied approval-mail evidence for `ezimageai.com`: Native Banner placement `31667650` and Banner 728 × 90 placement `31667651`, approved at 2026-10-11 03:26:18 UTC (Gmail message `1a128ff3f8f42966`). This verifies the approved types, not the association between placement IDs and loader hashes.

The component is imported only by the ordinary editorial article renderer. The directory, homepage, tools, account, pricing and payment routes do not import it. Photo Ideas and Raindance return their embedded tool renderers before the advertising component. No scripts were put in a layout, GTM or global provider.

Even with the server switch enabled, existing optional consent alone does not load ads. A reader must separately choose **Show blog ads** for that article visit. The choice is not persisted in a new cookie or storage key. Hide, consent decline, route unmount, cached-route hiding and pagehide tear down the browsing contexts; returning to an article requires another choice. Each frame is created and destroyed by its own effect, rather than relying on removal of a vendor script element.

Frames use only `sandbox="allow-scripts"`, an opaque origin and `no-referrer` both on the frame and within its document. Their `src` is a `data:` URL containing only the static advertising document: no article URL, query, account identifier, prompt, photo or signed asset URL is interpolated. This replaces the earlier `srcdoc` transport because an opaque `srcdoc` still exposes the embedding page's fallback base URL through `document.baseURI`. A removable `<base>` is not a reliable fix. Popup, top-navigation, form, download and same-origin permissions are not granted. A fixed 90px banner slot and 320px widget slot reserve space; the latter is a provisional clipping boundary, not a verified native creative height. Banner creation requires actual container width >=728px, and the banner is omitted on narrow screens. Intersection visibility gates initial loading without refreshing ads on scroll.

The public article canonical is not confidential. The transport correction prevents accidental exposure of private values if a reader's article address carries query parameters or a fragment; the probe used synthetic markers, not actual account or media data. A loaded child can still see the public parent origin through `location.ancestorOrigins`, without the parent path or query. This small URL-construction change does not introduce an ad server or alter the application's CSP. See [the local URL-isolation probe](evidence/blog-ads/srcdoc-base-uri-probe.json).

The application's CSP was not changed. The current implementation fails at the parent `frame-src` boundary: that directive allows only `https://challenges.cloudflare.com`, rejects the prepared `data:` document, and prevents its supplier scripts from running at all. The earlier `srcdoc` fixture instead inherited the parent script policy, which excludes both supplier hosts. A flag alone cannot enable working inventory. A browser error document is evidence of rejection, not of usable advertising. Empty `blockedURI` or `blockedURL` fields are not accepted as sufficient proof of either rejection or success.

The smallest candidate for future activation is a static ad document on a separate origin, for example a newly configured `https://ads.ezimageai.com`, without private inputs. It would retain the opaque sandbox, no-referrer, consent and per-visit choice. The concrete parent policy change would add only that origin to `frame-src` on ordinary editorial article responses: current `frame-src https://challenges.cloudflare.com` becomes `frame-src https://challenges.cloudflare.com https://ads.ezimageai.com`. Homepage, tools, account, pricing and checkout responses would retain their current policy. Article entry and exit would require full document navigation so the correct response policy takes effect; a document's CSP persists across SPA routing.

Each separate HTTP ad-document response can have its own CSP: the banner document's `script-src` allows `https://www.highrevenueformat.com`, and the native candidate document's allows `https://pl31768149.profitableratecpmnetwork.com`. This permission is local to the corresponding advertising document, not the root layout, article script policy, GTM or product scripts. Inline configuration can use a response nonce rather than a broad inline allowance. Creative image/frame/connect sources must be limited to domains established by a successful passive inventory review, with no automatic broad `https:` approval. A child response or meta policy cannot override the ancestor's `frame-src`; the parent article allowance is still required. The main application's `script-src` does not need supplier hosts in this architecture.

The smallest decisions for the parent to request are: approve that dedicated origin and static-document deployment; approve only the article `frame-src` addition and full document navigation at article boundaries; then approve a concrete observed creative-domain allowlist after the exact loaders return content. No ad account/unit, popunder/social-bar/notification permission, same-origin sandbox permission or new mobile parameters are part of this choice. Compatibility with this strict isolation is not yet known. All these changes remain unimplemented and require approval; if a supplied placement needs prohibited behavior or broader host access, leave it disabled. Actual inventory, placement-ID mapping, native/mobile rendering and request/cookie/redirect checks must pass before activation. Retaining the current policy with both flags false is the independently releasable news option.

Both loaders returned zero-byte responses in passive supplier checks: PowerShell HTTP 403 (including a final check with the publisher-origin Referer) and Playwright API HTTP 200. Therefore no real native cards, creative dimensions, third-party cookie chain, popup/redirect attempts or revenue can be certified. Do not treat an empty frame, a local canary or the approval email as successful advertising integration. Obtain nonempty exact-loader inventory, map the approved placements and passively inspect mobile rendering and request/cookie chains before activation. Prohibited creative behavior should keep the affected placement disabled; do not add sandbox permissions or new mobile placement parameters to make it render.

See [supplier HTTP, browser, screenshots and limitations](evidence/blog-ads/README.md). The privacy disclosure identifies the disabled state, optional choice, supplied domains and unknown inventory; it does not claim a completed live integration.
