# 图片生成两段剩余延迟调查

样本任务 `cmwiojhwg0002psp7x4ojlhve`，线上版本 `96c2f8f1`，登录用户 MiniMax H3 1K。
这份记录是对已有样本的只读调查，不是新代码上线后的测速。

## 点击到 Kie 建单

| 区间                       |      耗时 |
| -------------------------- | --------: |
| 点击到提交请求身份验证完成 |  2.169 秒 |
| 限流、幂等查询、配置       |  0.442 秒 |
| 资格预检                   |  1.172 秒 |
| 文字审核                   |  3.316 秒 |
| 建任务事务整体返回         |  4.503 秒 |
| 事务返回到调度子任务开始   |  1.415 秒 |
| 调度子任务开始到 Kie 建单  |  4.490 秒 |
| 合计                       | 17.507 秒 |

17.507 秒止于 Kie `createTime`，不能据此认定模型/GPU 开始计算。
`admission.waffo` 是沿用的计时名称，当前默认文字审核为 SeeAPI，Waffo 仅作指定技术失败的备用；不能把 3.316 秒全部归给 Waffo。
`background.dispatch` 和 `dueToStartMs` 有重叠，不能重复相加。

查到的可优化处：

- Generate 当前先等待重复提示词检查再提交。可提前检查并绑定用户、完整提示词和操作版本，保留重复付费提醒。
- 固定报价形成后，资格预检和文字审核可以并行；按本样本最多覆盖约 1.172 秒，但资格失败的请求也会产生审核调用。
- 任务事务内有效订阅被资格与存储上限逻辑分别读取，ROOT 编辑根资产与完整输入也有重复读取，可以复用同一锁后事实。
- 新 job 的积分预留仍执行通用重放查询。若优化，需私有新建证明和财务并发回归，不能直接删掉幂等保护。
- 调度准备与 claim 有重复投影，可合并读取，同时保留当前状态和提交不确定性判断。

目前没有逐 SQL、连接等待、锁等待与供应商 POST 的独立计时，不能给上述项目承诺总共节省多少秒。

随后已在本地实现登录用户草稿提前准备、资格与文字审核并行、订阅/ROOT 资产查询复用和调度投影精简，见[实现链路与验证边界](./image-admission-preparation-2026-11-16.md)。通用积分预留与现有工作流领取协议保留；本调查的数值仍是旧线上样本。

| 状态响应到浏览器图片 responseReceived   | 3.055 秒 |

原图请求 `2cdbe6b390698957629f53bcb091b6a7` 的 Worker wall=2696ms、CPU=1463ms；Hono 内部为 2.004 秒。
接口有 asset+审核证据读取、origin 读取、取图、再读一次 asset+审核证据的串行等待。框架初始化、SQL、R2 打开与可能的源站回退尚无分段测量。

该样本 R2 在 03:05:05.143 UTC 完成，比 READY 返回早 5.132 秒。匹配回执时既有 R2 分支已经流式返回，不执行整图 hash；缺少实际命中分支记录，不能把 2.696 秒归因于完整文件校验。
SeeAPI 回调比主动查询 ALLOW 晚 11.917 秒，因此保留主动查询。
结算晚于取图响应，未挡住该样本。

本次输出改造采取：审核通过结果独立发布、原图路由直接进入 Worker、批准原图流式读取。上线后仍需测量 responseEnd、解码与实际可见时间；responseReceived 只是收到响应头。
