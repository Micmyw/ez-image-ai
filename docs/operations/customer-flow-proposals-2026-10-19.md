# 生成体验后续方案（2026-10-19）

以下两项仅供方案评审，当前暂停实施与上线。取消全站单日限额属于独立、已授权的补丁，不与下述方案捆绑。

## 1. 登录用户：一次生成只做一次原子受理计数

**建议口径：计数代表一笔成功受理的生成请求；报价、安全检查、状态查询和同笔重试均不新增计数。** 它与图片/视频共用的账户积分、积分预留和最终结算分别记录。

- 报价保留鉴权、可用性、余额与安全检查，但不扣生成计数。提交时可以重新检查这些条件，重复检查不产生重复扣减。
- legacy「报价后提交」与 merged `submitGeneration` 统一进入一个受理事务；不靠删除其中一次调用实现“少扣一次”，而是明确各层职责并收敛唯一计数入口。
- 事务先按账户与稳定 `idempotencyKey` 查重并校验输入指纹；新请求在同一数据库事务中完成限额检查及一次递增、任务、输入绑定、积分预留与持久执行意图。任何一步失败全部回滚，避免“计数扣了但任务没有”。
- 同一 key、同一输入遇到双击、并发、断网重试或 legacy/merged 交叉重放，返回原任务，不再计数、预留积分或创建任务；同 key 改输入明确返回冲突。后台重派发也沿用原任务与执行身份。
- **失败语义：** 受理事务提交前的拒绝与回滚计数为 0；任务已受理后失败仍只记录这一次受理，同任务恢复不新增。积分释放、退款或不确定受理对账沿用现有幂等结算规则，不把受理计数当积分扣款。

验收重点：报价次数不影响计数；两种入口、并发重试与丢失响应均只产生一次计数、一笔积分预留和一个任务；事务失败三者均不落地；安全条件变化仍会在提交时拦截。

## 2. 游客：审核超时后继续同一上传与审核

**建议体验：** 短时间轮询结束后显示“图片仍在审核，可稍后查看”，保留草稿并提供“查看审核进度”；不把尚未结束的审核显示成上传失败，也不要求重新上传。

- 第一阶段在当前页面内存保存已有上传与 completion 身份。再次查看只轮询同一审核，不重新哈希、申请上传许可、PUT 文件或消耗新验证 token。当前本地代码已实现部分路径，仅供审查，尚未授权上线。
- 恢复必须绑定原 File 对象、文件哈希、规范化指令、模型/SKU、输出参数、capability 版本和有效期；点击时再次校验。失配或过期须明确提示重新准备，不能继续显示“无需重新上传”。后端继续复核上传凭证、来源、所属身份、capability、当前审核证据与一次消费状态。
- 页面刷新或离开后的恢复作为第二阶段：由服务端保存短期状态，以不透明恢复句柄和受保护的同源会话凭证重新授权原上传。不能仅凭 URL、客户端缓存或另一位用户的登录状态恢复，也不将 completion token、私有文件或指令写入 URL、日志和 localStorage。
- PENDING 保留恢复点；READY 原子消费一次 completion 并进入原有 handoff；明确拒绝、失效或其他终止错误清除恢复点并说明下一步。新验证回调不得覆盖审核等待提示。
- 查看审核不创建生成任务、不预留或扣积分；审核完成后的 handoff、创建任务及结算各沿用稳定幂等身份。并发点击、页面恢复与丢失响应应返回同一草稿/任务，避免重复许可、重复任务和重复扣款。

验收重点：多轮超时后仍只有一次上传许可和一次 PUT；有效恢复无需新验证；指令/文件/参数/身份/capability 改变及过期均正确拒绝；并发 READY、响应丢失与恢复不会重复消费或生成。
