# 生成链路一秒预算：目标、架构与验收边界

日期：2026-10-22，更新：2026-10-23。状态：v9d 预审核失败现场及 v9e/v9f/v9g 断点证据保留。真实生成后的本轮修复已完成 50 个独立用户的固定外部夹具本地样本，50/50 成功；这不是新旧版本对照或生产容量证明。系统附加耗时的一秒目标尚未认证。本文承接[第一性原理复核](./generation-performance-first-principles-2026-10-22.md)。用户已授权按计划修复；本轮不含提交、推送、部署或真实付费供应商调用。

2026-10-23 真实生成后的修复与证据边界见[结果交付后续修复](./generation-live-followup-2026-10-23.md)。真实本地 Workflow binding 接受现有带冒号事件名；REST 规则不能单独用来认定生产 503 的根因，因此本轮不迁移持久化事件协议。

用户最新明确：**保持模型与完整结果，将外部模型/审核处理、必要数据库 I/O 和必要网络传输的客观耗时单列，系统自身增加的计算与等待总计 ≤ 1,000 ms，并尽量继续降低。** 这取代上一版把必要查询、完整图片下载也放进一秒预算的口径。一秒是上限，不是允许各环节花满的额度。不能用更换模型、降低输出质量、未审核预览或缓存命中替代这个目标。

随后用户明确要求去掉人为的系统级并发限制，至少支持几十人同时使用。本轮以 **50 个独立用户同时提交并完整完成生成、两次审核、私有图片展示及账本结算** 为本地并发验收目标，失败、拒绝和未完成的请求都保留在分母中。此前提出的 control `3+1` 槽位预留已撤销；新的轻型执行按请求独立调度，不经过全局 control `4`。真实字节/内存约束、供应商实际配额、数据库租约和账本幂等仍是正确性条件。结构改动及一次本地测试都不能证明生产上的无限容量。

## 计时合同

| 指标                   | 起止与计量                                                                             | 目标                                |
| ---------------------- | -------------------------------------------------------------------------------------- | ----------------------------------- |
| 可控附加耗时           | 点击 → 完整获准结果渲染，扣除关键路径上可证实的外部处理、必要数据库 I/O 与必要网络传输 | 总计 ≤ 1,000 ms，并继续压缩         |
| 每次审核发现的可控耗时 | 审核完成 → 认证取得并提交有效证据，扣除必要 I/O；分别记录输入、输出                    | 各 ≤ 1,000 ms，且共同占用上述总预算 |
| 重型槽的可控占用       | 实际持槽区间扣除必要 I/O；同时累计一次请求所有重型区间                                 | 每请求合计 ≤ 1,000 ms，尽量缩短     |
| 审核占重型槽           | 首次审核请求、外部审核等待、结果查询和证据收尾与重型槽的交集                           | **0 ms**                            |
| 完整墙钟时间           | 点击到完整可见、每次审核完成到证据提交、实际持槽时长                                   | 原始时间完整报告，不扣除任何耗时    |

可控部分包括：不必要的查询和下载、连接/任务反复初始化、额外调度交接、软件排队、轮询和重试空档、无依赖工作的串行化、冗余解析/检查，以及浏览器状态发现和渲染延迟。审核结束后等回调调度、轮询或 Workflow 恢复，不能继续算作“外部审核处理时间”；调度平台的等待也不能仅因平台在外部就全部豁免。

**先优化必要工作集合，再扣除其中的客观 I/O 时间。** 不能把当前所有 SQL/HTTP 用时一概从预算中减掉。重复关系加载、可以合并却分开的查询、无效扫描、多余 HEAD/GET、重复下载，以及不合理的事务范围和池配置引起的等待，仍属于优化责任。必须同时报告查询/传输次数、字节数和总 I/O 时间；缺少证据的“不可避免”不作豁免。

并行分支只扣除真实阻塞最终结果的必要区间，按关键依赖和重叠区间去重；不能把所有外部调用时长直接相加。点击前的素材上传/预检另报完整时间，点击后剩余等待也按相同口径分类。外部完成时刻或数据库分段没有可信证据时，标记为不可精确拆分，不用首次成功查询时刻反推“刚刚完成”，也不把整个客户端数据库 span 直接视作客观耗时。

本地报告另给保守的剩余端到端墙钟上界：只扣除逐任务身份和唯一角色匹配、明确声明固定处理时长的外部夹具区间并集，全部 SQL、存储、HTTP、排队、解码和显示时间仍计入剩余值。Kie/SeeAPI 采用材料读取之后的 acceptedAt 加配置处理时长；新 Waffo 样本使用显式 plannedReadyAt，旧样本没有声明则不扣。绝不扣除本机 timer 晚触发、POST 响应延迟或回调调度。起止采用 epoch 与浏览器单调计时的较大值，并记录差异；无法对齐时钟、失败、超时和遗漏样本不提供有限成功上界，但仍保留分母。该值 ≤1 秒只能支持相应本地样本的保守时延结论；大于 1 秒也不能反推可控开销一定超标，因为必要 I/O 尚未扣除。它不是累计 CPU/SQL 时间，也不自动开启 `oneSecondCertified`。

这是成功交付的时延目标。超时返回、拒绝请求、显示占位符和把同一任务拆成多个小槽，都不算一秒成功。

## 用必要工作反推实现

撤销上一版混合数据库和传输时间的逐项毫秒分配。先按以下结构目标删除工作，再用分段实测确定各阶段还剩多少可控耗时；总额仍不能超过一秒。

| 优先级 | 正常路径目标                               | 判定方法                                                         |
| ------ | ------------------------------------------ | ---------------------------------------------------------------- |
| 1      | 固定轮询/容量睡眠不再决定正常推进时机      | 完成通知、资源释放到下一步开始的 trace 中没有人为固定空等        |
| 1      | 审核、模型等待不占用不需要的重型资源       | 审核与重型槽重叠为零；同步大响应适配器先证明有界处理再拆分       |
| 2      | 同一阶段不重复创建调度实例或加载完整上下文 | 每任务一个持久执行身份；后继复用已提交的最小状态                 |
| 2      | 不重复取得同一不可变事实                   | 相同身份/规则/有效期下复用检查凭据；每个 SQL/HEAD/GET 有具体用途 |
| 3      | 无真实依赖的工作并行或提前完成             | 审核分支按冻结输入独立执行，汇合处保留必要复验与证据             |
| 3      | READY 后立即触发页面读取和展示             | 已提交状态通知驱动，轮询只做恢复；完整解码仍是展示终点           |

每个操作只归属一个阶段；READY 若已包含在审核证据事务中，不再重复计数。现有回调样本的两个发现间隔为 358/343 ms，尚未包含完整证据落库，也没有拆清必要 I/O 与可控开销，不能拿来证明新口径的一秒目标已经达标。

## 必须一起改变的执行结构

### 1. 正常推进直接执行，持久记录负责恢复

新的版本化图片执行协议应以 PostgreSQL 中的阶段、版本、执行意图和租约为唯一依据。一次阶段提交返回下一步需要的最小状态，持有有效执行权的运行器直接继续；真正等待供应商或容量时才交还调度。每个任务保留一个持久 Workflow，Outbox/恢复消费者继续处理崩溃和丢失的唤醒。

Outbox 的必要性是事务性记录“已经发生的业务变化还要求执行什么工作”，不是全局扫描或固定轮询。业务事务和外部 Workflow/消息队列不能一起原子提交，单纯删除 Outbox 会留下“扣款/创建成功但任务未发出”或“已调用供应商却重复调用”的恢复缺口。可以把意图合并进阶段执行表，但仍需原子写入、唯一身份、领取租约、完成回执和重试恢复；那是另一种持久执行意图实现，并不免除这些必要工作。本次保留既有协议，正常路径直接使用本次事务实际插入的事件 ID，恢复才查找未完成工作。

回调接收器通过 service binding 调用共享的轻型结果处理入口，领取同一阶段的执行权后立即认证查询、提交证据及后继意图。正常发现路径不必先创建新的唤醒 Workflow 再层层领取事件。原 Workflow 与直接入口使用同一状态推进和去重机制，不能各自提交模型。Workflow 事件可用来唤醒原实例，但其恢复延迟必须实测，不能假设天然是几十毫秒。

数据库按事实边界使用短事务：领取执行权/持久提交意图在外部调用前，结果证据/状态/后继意图在外部调用后。外部请求不占数据库事务。缩小投影、条件更新返回后继数据、合并同一事实提交；保留账户锁、退款/删除复验、未知受理和稳定账本引用。`max: 1` 连接上的 `Promise.all` 不能消除 SQL 往返。

新建报价且文本审核 `ALLOW`、技术失败次数为零时，原本跨用户的 provider/stage 事故独占锁改为共享锁；无事故的正常提交可以并行。已有事故的恢复仍先取行锁、按原 activeKey/lastFailureAt 条件领取并在同事务写一次恢复 Outbox。失败和历史审核继续独占，不能在共享锁内升级独占锁。账户、资产和显式配置的全局费用预算锁维持各自真实业务约束。

首次 SeeAPI 图片审核同样移除正常成功事务的跨用户独占锁：只在已持有资产锁、无历史审核、检测完整且结果 APPROVED、服务正常响应、零技术失败、无 bypass 时使用共享锁。审核证据、READY、事故恢复及后继意图仍一起提交；失败、历史审核和管理员处理继续使用原互斥规则。真实 PostgreSQL 回归同时验证两个不同用户完整审核事务可以重叠，以及未提交证据不可见和回滚。

图片、普通视频和模板场景的供应商提交不再获取退休容量计数对应的 provider 全局锁，也删除只为该锁进行的重复路由预读。保留每个 job/attempt 的执行权、资金和真实费用预算约束；同一个任务的并发领取仍只能产生一次提交，未知受理仍不能重提。

50 用户实测暴露出另一个独立问题：Serializable 对全表/页级读取的冲突检测会使不同 owner 相互重试，索引存在也不能保证查询计划避免它。后续采用独立的 `media_owner_storage_fence` 表，在原 owner advisory 锁之后原子递增该 owner 的 revision。旧 Serializable 事务若在等待期间拿到了陈旧快照，会在该行写入时真正冲突并重试；允许使用 ReadCommitted 的新路径则在锁后用新语句读取额度。这个记录没有全局计数或并发上限，不存放积分或伪造存储预留。

新隔离路径由默认关闭的 `MEDIA_STORAGE_FRESH_READ_ENABLED` 控制发布兼容性。提交只开放精确匹配的首次 CREDITS 临时参考图 ROOT 请求：原分支在同事务创建新资产和审核事件；v9e 另允许复用身份完整匹配、第一代正常审核已通过的 ACCOUNT/INPUT/legacy 素材。复用必须取得审核锁并执行条件资产写栅栏，再以新语句读取当前身份和完整审核证据；仅行锁不能使旧 Serializable 删除事务的快照变新。未知受理、活动租约、后续审核代次、管理员或 bypass 历史、重试/子任务、Image Pass、未知字段及全局预算仍保留原隔离。输出存储领取/完成保持 owner、资产、租约和条件更新保护，并对资产取得行锁以协调游客过期回收。不能只改隔离级别而让旧额度写入者继续绕过新 fence。

锁后的有效期判断使用真实数据库时钟，而不是固定在事务起点的 `CURRENT_TIMESTAMP`。新的输出预留/完成分支先取得 owner、binding、资产行锁，再用 `clock_timestamp()` 检查租约和游客保留期限；新建提交在积分和审核等全部可能阻塞的写入完成后、返回前复核报价及临时素材期限，超期整体回滚。真实 PostgreSQL 回归覆盖锁等待跨过截止时间；不能以降低事务隔离为由放松到期、余额、资产或回执约束。

测量实际 SQL 数、连接/锁等待和执行位置到数据库的 RTT。先减少可消除的往返、缩短锁持有时间和投影，再单列剩余必要 I/O。区域迁移属于可另评估的基础设施收益，不作为当前软件优化的前置条件。不能用查询缓存、取消授权或自动切换未知受理任务的运行时来补数字。Hyperdrive 连接仍在各自 Workflow step 内创建和使用。

### 2. 审核完成通知必须被记住，不能只盼下一次重试

方案制定时的 `wakeImageModeration` 遇到未绑定 task ID、未知受理或活跃租约时返回 `pending`，HTTP 接收器随后返回 503。新实现把首个有效通知存入当前代次的 `verificationCallbackReceivedAt`，早到或活跃租约返回 202，不依赖供应商重试唤醒。租约领取时捕获通知时间，PENDING 提交与回调在同一 advisory lock 下协调；查询期间新到的通知保留立即重查时间，重复通知不反复拉高查询频率。

新协议应在校验签名及资产/审核代次/提交身份后，持久记录去重的待处理唤醒，例如带代次的 `wakeSeq`。回调不携带可信业务结论。已有执行者结束查询时，只有它读取的通知版本仍是最新版本，才允许把下一次查询时间推远；有新通知就保留立即查询意图。早到通知在合法 task ID 绑定后被消费，未知受理仍按原恢复规则处理，不能凭回调解除未知状态。

新的轻型提交、查询和证据提交进入 `ControlExecutor` 独立服务请求，经同脚本 `JOBS_CONTROL` 绑定调用，取消全局四槽及三加一预留。旧 `jobs-control` 接收端保留用于旧 Workflow 排空；同一个业务任务的执行权仍由数据库租约决定。通过阶段租约、请求去重和真实供应商预算避免重复查询。普通视频的输入图片审核也接入匹配的回调。

当前启用的 Kie 生成完成通知也持久化：复用 `ProviderWebhookEvent` 中独立的 `kie-image-completion-notice` 通知类型，按 attempt/task 去重，不新增 Kie 数据库字段，也不把通知当作供应商结论。早到通知等待真实提交绑定；查询领取时原子消费，查询期间新到的通知不能被 PENDING/error 延迟覆盖。已绑定但尚未消费的重复通知可以重试直接唤醒，以修复前一次通知传输失败；已经消费的重复通知不再改变查询时间。未知受理仍不能凭通知解锁或重提。

查询期间到达的有效回调不再被固定最小轮询间隔推迟。新调用方在签名执行信封中显式发送 `supportsImmediatePolling: true`，接收端才可返回 `waitSeconds: 0` / `retryImmediately: true`；旧 Kie/审核调用分别保留五秒/一秒的协议兼容。Kie 在成功查询释放租约后最多在同次请求补查一次，再交给有调用次数/时间预算的续查。审核仅在成功 PENDING、已绑定任务、非未知受理、租约已释放且数据库查询时间已到时立即续查，下一次强制 `queryOnly`。失败退避和未来查询时间继续生效，不能重放首次提交。

只有回调无法保证丢回调场景也在一秒内。备用查询间隔、调度空档、认证查询及提交中的可控部分仍共同占用一秒预算；只有必要 I/O 单列。例如每 250 ms 查一次，N 个在审任务约增加 4N 次查询/秒；这只是容量算式，不是已批准或已支持的供应商调用频率。必须遵守真实配额和 `Retry-After`。供应商不提供足够及时的回调或允许的查询能力时，分别标明供应商限制与内部等待，继续可靠恢复，不能把所有轮询等待都扣成客观耗时。

当前 [SeeAPI 图片审核文档](https://www.seeapi.com/docs/nsfw-filter/image-moderation/)规定常规受理返回 202，通过回调通知和认证 GET 取回完成结果；没有在该页面找到亚秒送达承诺。现有“同步响应若已经带完整结果则直接消费”的优化应保留，但不能把夹具的同步成功当作真实供应商默认行为。

### 3. 让重型资源只服务实际图片处理

原 [runtime.ts](../../packages/jobs/src/runtime.ts) 在转存后直接执行首次审核。新路径先完整检查并提交私有转存身份及审核意图，释放实际传输资源；首次审核、等待、查询和证据提交在控制路径执行。若缺少可信检查凭据、需要补做重型检查，必须作为独立受控检查阶段完成，不能藏在轻型审核里。

普通已知长度、无需变换的 URL 图片进入 `TransferExecutor`。SQL 先验证并投影有界 remote URL，避免读入历史 Base64 envelope；实际响应长度和 MIME 合格后才取得传输租约。源流和条件 PUT 共同背压，在既有 25 MiB 上限内不再分配整图 Buffer；哈希、魔数和实际长度校验贯穿传输，最后一个字节等待源 EOF 与验证通过后才送出。失败不得成为 READY，冲突时全量验证实际 winner。任一不兼容条件在本次传输领取前返回明确的重型路径选择，保留相同 task/receipt/attempt；网络错误不能触发这种转换。

最后一张普通输出审核通过时，在同一事务仅依据完整的私有输出身份、候选数量/位置和当前审核证据完成持久化检查并创建结算意图，省去正常路径第二次重型 finalization。缺失或历史不匹配状态继续完整处理；账本结算仍独立复验。

用户进一步指出当前没有启用 Gemini/OpenRouter 直连。核对当前仓库环境源：`MEDIA_ENABLED_PROVIDERS=kie`、`MEDIA_RECOVERY_PROVIDERS` 为空、`MEDIA_OPENROUTER_IMAGE_ROUTES_CERTIFIED=false`。当前图片执行走 Kie，Nano Banana 等模型的名称不代表走 Gemini 直连。同步适配器不是当前已启用路径的瓶颈；本轮撤出针对它们新增的暂停/重领槽状态机，保留此前存储流水化等实际路径改动。该核查不是线上运行配置验收。

若未来启用同步直连，再单独验证有界响应处理、Base64 膨胀、缓冲保留、断流和未知受理边界。当前函数不能直接改为 control：多个完整 JSON/Base64 响应仍可能耗尽同一 isolate 内存，不同 DO 名称不构成隔离证明。这是未来准入要求，不计入当前 Kie 链路的性能缺口。

普通未变换图片继续尽量一次有界源流、一次完整检查、一次条件私有写入；已有凭据只在身份完全匹配时复用。容量释放立即唤醒等候者，替换固定五秒空等。槽位最终只在资源实际释放后归还，不以 `Promise.race` 一秒超时假装任务已经停止。

### 结算冲突与审核快照的独立反例

结算的首次读取已缩小为 job 和输出资产 ID，仅用于确定锁集合；完整资金与审核证据仍在锁后读取。独立 PostgreSQL 诊断没有证明此投影变化能解决并发冲突。最新 50 个不同 owner 的三组对照中，原路径为 7 个成功、184 次序列化冲突，缩小投影后为 4 个成功、190 次冲突；仅在测试代理内跳过已知新结算的账本负向查询，仍为 4 个成功、190 次冲突。因此“删除这次账本查询即可消除争用”的假设被否定，生产账本重放校验保持不变。该诊断只执行结算，不包含模型、转存或浏览器。证据为 `settlement-negative-lookup-pg-v3-evidence.json`，原始失败保留。

同一诊断还复现了独立的正确性问题：ReadCommitted 审核写入者持有资产审核 advisory 锁，把资产改回 VERIFYING 并递增审核代次；Serializable 结算事务先取得旧快照，再等待该锁。审核提交并释放锁后，结算仍能读取旧的批准证据，单次提交为 SETTLED，且没有序列化冲突。仅有 advisory 锁不足以使旧快照失效。修复必须让这种并发修改导致整笔资金、账本、任务及后继意图回滚，并在新快照上重新校验，不能通过放宽审核判定或资金隔离绕过。

修复在结算的最后一个数据库操作校验输出资产行版本，采用 `FOR UPDATE NOWAIT`，并仅让结算在原有总尝试预算内重试已确认回滚的 `40001` / `55P03`。不使用阻塞式末尾行锁：游客清理可能先持有同账户输出资产 A，再为另一未提交任务 B 释放积分而等待账户；结算若持有账户后阻塞等待 A，会形成相反锁序。未知网络或提交结果不能因此重试，缺失输出行也不能作为校验成功。

真实 PostgreSQL 正确性回归为 **9 项通过、2 项诊断用例未启用**。CREDITS 与 IMAGE_PASS 两条分支均复现 `40001` 后重新校验，失败尝试的账本、批次、预留、任务与 Outbox 全部回滚；四次 `55P03` 耗尽后，事件仍 PENDING 且资金未改，释放竞争锁后可继续同一结算。真实游客清理的两任务交错出现 `55P03`、随后 `40001`，第三次完成释放，没有死锁；退款先后与取消交错也通过。物理删除输出被已有不可变审核外键及删除触发器阻止，缺失/错误资产集合的防护由单元测试覆盖，不能标作真实物理删除验收。证据为 `settlement-fence-interleavings-pg-v10-evidence.json`。这证明相应并发正确性修复，尚未证明结算吞吐或完整 50 用户、一秒目标达标。

### v8 关键路径复核：24.9 秒不能全部归因于数据库

### v9 恢复、v9b 对照与 v9c 审核提交优化

### v9f 编译器复用：产物验证与 ABBA 对照

纯 raw SQL 延迟初始化的分支证据目前只覆盖 50/486 个请求；另外 36 个没有供应商查询的 poll 不能据此归为 raw-only。当前选择在固定 Prisma 7.9.1 edge runtime 中复用已构造的查询编译器，并保留独立客户端、查询计划缓存、参数、适配器、连接和事务。每个构造器仅保留第一组完整匹配的受支持元数据；同步借用仅覆盖 compile/compileBatch，忙碌、重入或不匹配时即时创建独立对象，不加入全局等待队列。

### v9g 审核及提交前重复工作消除

v9g 的审核 query-only 领取在取得原 verification 锁后，用一条参数化 SQL 读取资产、当前活跃 owner、ERROR 次数及历史/copy 标记。正常已绑定且无历史转换的账户 INPUT 领取从 9 条语句减至 5 条，OUTPUT 与临时 INPUT 从 8 条减至 5 条，不含事务 BEGIN/COMMIT。仍保留进入业务前的 engine observation、完整 owner/数据库时间读取、owner CAS、资产写入和最终 GET 前的所有权检查；过期 owner 行的 epoch 不得由活跃 owner 投影替代。领取期间新写入 ERROR 或改变代次后，旧投影立即失效。

成功 verdict 的资产、ERROR 和前次 review 证据合为一个锁内投影；普通无 copy 输入省去前后两次 pointer 缺失查询。相应读取组 OUTPUT 为 3→1，INPUT 为 5→1，其余 incident、不可变证据、锁顺序及同事务 continuation 保持。copy pointer 与目标资产在同一事务创建；只有本事务确认的无 copy 情况走短路径，存在或异常 pointer、历史及管理员处理继续原协议。查询既有 SeeAPI task 时也不再生成 retrieve 不使用的图片签名 URL。这些是结构性语句减少，不代表已测得固定节省秒数。

生成 claim 的原 pre-send 写入返回 PostgreSQL attempt/job 的 `xmin`；事务确认成功后，当前 store 才签发内存内证明。证明绑定实际 claim 对象，规范化为冻结的纯 JSON 副本，并在首次 await 前消费。提交前仍以新事务锁定 attempt，再以新语句检查两行版本、owner epoch、数据库租约时间、任务状态及指纹；不再完整读取并重算、重写同一 pre-send。复制、跨 store、重复消费或状态变化的证明不能授权调用模型，旧调用者仍执行完整协议。证明不进入 RPC、数据库或客户端，不增加任意 TTL；`xmin` 为现有 PostgreSQL 系统列，不要求新 schema migration。未知事务确认仍走现有 uncertainty/恢复协议，不能描述为自动即时恢复，也不能重发付费请求。

上述审核与提交前改动已通过 107 项唯一单元用例、178 项唯一真实 PostgreSQL 用例及相关类型检查；候选 Workers、hybrid Worker-only dry build 和实际制品 workerd/PostgreSQL 冒烟通过。独立审查未发现范围内新增阻断项。`xmin` 标识事务而非每次 UPDATE；该证明依赖当前准备事务在捕获版本后不再修改 attempt/job。仓库迁移中的相关触发器已核对，不代表已检查线上额外触发器。

独立查询计划诊断 `plan50-v9g-diag01` 已完成 50/50，普通制品不带诊断。500 个实际独立客户端共记录 4,500 次成功编译器 facade 调用；74 个参数化形状中，同一客户端内没有重复编译，4,426 次是相同 namespace+shape 在不同客户端出现。普通只读动作占 33 个形状、2,250 次编译；前三个形状只占总编译数的 11.11%，不支持仅凭 model/action 大规模改写热点 SQL。精确调用点和 simple-SQL 分类尚未由计数证明。

### v9h 上传预审核反馈与接续精简

前述 26,721 ms 为冻结 v9f Worker 的两组 50 人点击到可见合并中位数，使用共同的最终 Node API/harness 和 `submit-time` 输入模式。该模式直接准备存储数据，未经过真实上传预审核；它不能解释用户上传后填写提示词时已经完成的审核。实际产品在不可变上传完成后开始审核，而不是在上传字节仍变化时给出审核结论。v9h 新增真实 `upload-reviewed` 和 `upload-pending` 场景，保留历史模式与原始失败证据，不重写旧基线。

上传反馈增加受保护且禁止缓存的最小状态查询。一次有界数据库读取校验当前用户、签名 token、对象 key/checksum/bytes/MIME、素材与预留期限，以及当前 generation/attempt/provider task/rule/policy 的审核证据。只返回 `NOT_STARTED`、`PENDING`、`APPROVED`、`REJECTED` 或 `UNAVAILABLE` 与公开拒绝原因，不返回私有地址或供应商内容。页面可见且审核未结束时每秒查询；审核中允许生成并复用原任务，确认拒绝或最终不可用阻断新提交，暂时查不到状态保留原提交能力，由 Generate 再次做权威检查。账号或图片变化使用独立查询 key；已有生成任务的两秒恢复轮询保持不变。本轮没有把所有任务失败通知改为实时推送。

Fused control 的原 begin `UPDATE RETURNING` 可同时返回不可变 engine 标识。成功确认原 receipt 后签发请求内、不可序列化且只能消费一次的证明，绑定同一数据库实例、精确 child 对象、完整 prepared payload/receipt 和执行上下文，仅消除首次审核及异步图片模型提交外层的一次 engine-only SELECT。query-only 审核保留完整 observation；缺失、外来 engine、旧调用、heavy、复制或变更的证明均回到原门禁。业务领取仍校验当前状态、租约和 phase owner。新事件保留 Workflow 身份，但不继承上一输入审核的 phase owner。未知 begin 不发证明；已完成事件只恢复已提交结果，不重放付费处理。

普通已验证 Content-Length 的私有图片转存，将资产/传输领取和精确容量预留放入同一事务，减少一次独立预留事务及其资产重读。保持 owner advisory lock、revision 写屏障、job/asset 锁和原隔离开关；配额失败整体回滚。本次新资产领取的预留只在同一调用、相同字节数下复用一次，消费发生在 await 前。恢复、已有资产、字节变化和第二次调用仍做原租约事务；最终完成继续验证 transfer token、数据库期限和足额 ACTIVE 预留。guest、未知长度、转换和 multipart 保留现有路径。

输出仍通过同一下载流并行计算校验和并写入私有存储，之后审核该不可变对象。SeeAPI 当前合同没有提供可将临时供应商 URL 的独立读取与最终展示字节强绑定的替代证据，因此本轮不把私有存储后的审核改成两次各自下载供应商 URL。审核“就绪”提示仍只唤醒认证取回；已认证同步完成的提交结果可继续跳过 GET。只有审核证据和下一步执行意图提交后才允许付费生成。

新真实上传场景使用默认上传 handler 和受保护状态查询，不手工植入 pending/approved 结果。`upload-pending` 按用户逐一执行上传后立即点击，核对点击时仍未完成审核、输入审核只提交一次且任务 ID 不变；若先完成则标记该场景未覆盖，保留样本，不筛掉或重试来制造结果。报告同时列出上传到可见、准备到可见、点击到可见与真实点击跨度。两种模式属于不同功能场景，不能相互相减为提速幅度，也不能直接同旧 `submit-time` 成绩对比。最终本地制品与完整链路结果另记在本轮证据中，未取得的系统附加耗时及线上一秒上限保持未认证。

这些改动直接接管对应正常入口，无需长期维护第二套普通实现；旧 Workflow、旧调用与已接受/未知任务依赖的分支在排空前仍保留。本轮不新增 schema、全局人数上限或供应商模型切换；既有迁移、开关和 receiver-first 发布要求继续适用，状态接口与前端需兼容发布。本地修改不等于生产版本已替换。

### v9h 真实上传并发发现的缺口

首个 `upload-reviewed` 50 人完整链路仅 **48/50** 成功，case17/23 在点击前收到 `MEDIA_REQUEST_CONFLICT`。私有输入对象已经写入，数据库仍为 ACTIVE reservation、owner fence revision=1 且没有 MediaAsset，表明上传后提交事务整体回滚；这两例没有生成任务、审核或模型提交。PostgreSQL 在上传窗口留下 69 次 Serializable 读写依赖冲突，其中 35 次发生于 COMMIT；这些是事务错误次数，不是 69 个失败用户。原始失败组、对象 HEAD、数据库现场和预算分析的失败退出都保留，不能用 48 个成功样本代替 50 人通过。

临时上传的 reserve 与 commit 此前未接入已启用的 storage fresh-read 路径。修复仅在既有开关精确为 `true` 时改用 `runReadCommitted`，保留 owner advisory/revision fence 与 asset-binding 锁；commit 另取 reservation 行锁后读取数据库时间，检查完整引用身份、24 小时 TTL 与 ACTIVE-to-COMMITTED 条件写。COMMITTED 重放不重复建立资产或审核意图，默认关闭继续原 Serializable，Generate 的审核证据和积分事务不变。上传 API 继续单次 reserve、单次不可变 PUT、单次 commit，不因未知结果重新上传。

定向真实 PostgreSQL 回归中，同一有效的 8 项检查在旧实现为 6 失败/2 通过，修复后为 8/8；包括 50 个不同 owner 同时 reserve+commit 全部成功，每人只保留一个资产和审核意图，以及同 owner 配额、重复提交、显式锁等待后过期和旧 Serializable fence 兼容。最终再加入 3 项旧 reservation writer 的 ACTIVE 终结兼容检查，共 11/11 通过；相关数据库单元 81/81、上传 API 20/20，以及数据库/API 类型与相关格式、lint 检查通过。该确定性并发测试与完整浏览器负载的启动方式不同，不能把其失败比例当作线上发生率。最初两项过期夹具没有保持签名引用的 24 小时创建/到期关系，已修正夹具并保留原失败，没有放宽身份断言。

同次复核还发现失败样本的准备结束时间沿用了 seed 初值，产生 -1901/-1830 ms。原报告保留，并将其解释为结束时间未知；新 harness 在准备未完成时记录 `null`，不填零、不删除失败或修改成功样本的计算。此前单人 pending 样本虽在点击前为 PENDING，但输入审核服务在点击后 170 ms 才受理；只能说上传触发了异步审核并复用原任务，不能把 PENDING 等同于供应商已在点击前处理。最终负载需另列实际受理早于点击的数量。

### v9h 审核中立即生成的准入缺口

修复临时上传并冻结 `v9h-final04` 后，`upload-reviewed-50-02` 完整 50/50 成功，点击到可见 P50/P95/最大为 11,258/11,726/12,212 ms；上传到可见为 18,482/19,617/19,647 ms，实际点击跨度 2,337 ms，峰值 50。该模式等输入审核完成后才点击，不能覆盖审核中提交的分支。

同制品的 `upload-pending-50-01` 只有 **19/50** 成功。50 人全部真实上传成功、点击前状态为 PENDING、各提交一次输入审核；31 例在 Generate admission 收到 `MEDIA_REQUEST_CONFLICT`，没有 job、生成 attempt、模型提交、输出审核或积分账本记录。成功 19 例各有一次 RESERVE 和 SETTLE。实际点击跨度 219 ms、峰值 50，完整分母和失败原件保留，不筛选成功子集作为验收。该窗口 PostgreSQL 留下 148 次读写依赖冲突，其中 87 次出现在 Outbox 查询、48 次在 COMMIT；这些是事务冲突次数，不能等同用户数或将全部原因归到单条查询。

源码确认已有临时素材复用门 `fencePreReviewedTemporaryInput` 只接受 READY，已存在的 VERIFYING 素材会回滚 fresh-read 事务并转入 Serializable。上一项修复覆盖上传 reserve/commit，未覆盖这个 Generate 分支。后续修复要求在原审核身份、verification 锁、条件资产写屏障、账务和期限保护下复用同一 PENDING 审核及原事件；创建等待中的生成任务不能作为审核通过，也不能重发受理未知或仍持租约的审核。截至这个失败阶段，两组模式尚未在修复后的同一制品上全部通过，一秒系统附加耗时未认证。

该准入修复在原开关下增加独立的第一代 VERIFYING 等待分支，覆盖尚未领取、已领取、首次发送中、已绑定供应商任务、已写入 PENDING 及正在查询六种正常状态。保留完整不可变身份、现行审核策略、原事件及任务号；资产条件写后重新读取证据，积分事务和最后数据库时间复核保持。首次 HTTP 请求前预先设置的 `uncertain=true` 不等同于历史错误，可以在有效租约和完整首次提交身份下仅绑定等待任务；数据库不能证明请求仍在网络中，即使进程刚崩溃也不得清除未知标记或授权重发。已记录 ERROR、过期未知租约、管理员复查、后续审核代次和不匹配身份继续原路径。

有效的同一组 13 项真实 PostgreSQL 回归，旧实现 11 项失败、2 项通过，修复后 13/13；最终扩展为 44/44（pending 24、READY 10、锁竞争 10），相关单元 120/120，数据库类型及格式、lint 通过。包括 50 个混合审核状态的不同 owner 全部一次事务准入，原审核 task/token/attempt/lease/phase owner/epoch/evidence/event 逐字段保持，以及审核先提交或准入先提交的竞态。旧 Serializable 删除快照保护保留；后续审核不会复活已取消/失败任务。独立只读审查未发现范围内阻断项，未重跑测试。最初两个回归夹具的 proxy 缺省参数及报价签名问题已修正，原失败与有效对照分别保留。完整新制品复测结果另记，不以这些数据库测试代替端到端并发验收。
