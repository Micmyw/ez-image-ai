# 正常操作即时推进与清理隔离

2026-11-15，本地实现，尚未提交或部署。保留工作区此前的 SeeAPI 持久化恢复修复及其他未提交工作。前置审计见 [后台扫描体验审计](background-scan-experience-audit-2026-11-15.md)。

## 行为

- 游客生成事务提交后，立即唤醒同一 `jobId/trialId`；重放仍使用原试用身份。接口不公开试用内部字段。准入返回的精确后续事件在正常执行和恢复投递中均继续执行。
- 草稿领取、游客登录移交后立即启动已提交的素材复制；复制后按原复制记录查回目标审核事件，直接接续。保留字节校验、租约、来源权限和完整审核要求。
- 已验证支付 webhook、PayPal 积分包和 Image Pass capture 持久化后立即唤醒支付处理；取消订阅和取消生成也在事务提交后启动。支付包不反向依赖 jobs；由 API 注入唤醒。供应商受理未知、所有权、账本幂等和取消能力校验均保留。
- 即时唤醒只等有界的调度受理，在托管请求生命周期内运行；失败保留原持久工作记录，注册生命周期失败只等待同一个 Promise，不重发请求。
- 游客准入、支付处理和取消等轻量操作进入请求独占 `JOBS_CONTROL`。清理使用独立 `jobs-cleanup`（单槽），每批最多 10 条；恢复扫描排除物理删除、分片终止、上传清理和素材复制孤儿清理事件。到期清理和恢复分别由独立 Workflow 执行。
- 全局扫描保留漏唤醒、中断、过期租约、对账及回执补记。正常操作不等待全局扫描。扫描可能读到已被即时任务处理的原恢复事件，由原有业务幂等保护完成回执；即时受理本身不会提前 ACK。
- 原图审核与归档并行、审核通过后可读的规则保持。不同执行通道不保证不同内存隔离，也不消除共用数据库、网络或大图处理的开销。

无需新表或环境变量。按本轮用户“工作流直接覆盖掉”的要求，不新增旧维护通道的接收兼容分支：游客准入、取消和支付只按新路由执行，恢复扫描不内联清理任务，清理使用自己的入口。未指定领取分区的底层接口保持原有行为。将来覆盖发布仍需一起更新 Jobs/Workflow 接收端与网站生产者；不能遗漏独立清理入口或接续消费者。回滚应同步恢复旧定时入口，避免遗漏清理；不改删除暂停开关。本轮没有执行提交、推送或部署。

## 模型完成到可展示：生产日志复核

生产仍是审计记录中的 `3fc8b3e`。以下为同三笔游客任务，UTC 时间；`completedAt` 是本站记录模型完成的时刻，并非供应商内部精确完成时刻。`verdict_committed` 为事务提交后记录的 READY 生效日志。

| 任务后缀 | 模型提交           | 本站记录模型完成 | 获取 ALLOW   | READY 提交完成 |
| -------- | ------------------ | ---------------- | ------------ | -------------- |
| 1j8396ju | 11-14 19:58:22.724 | 19:58:57.572     | 19:59:20.842 | 19:59:24.093   |
| mzb9nljf | 11-14 21:00:02.979 | 21:00:30.494     | 21:00:55.734 | 21:00:59.064   |
| dytxkc27 | 11-15 02:59:50.456 | 03:00:15.741     | 03:00:40.391 | 03:00:43.588   |

三笔平均：提交模型至本站记录完成 **29.216 秒**，此后至 READY 生效 **27.646 秒**，合计 **56.862 秒**。此前按审核证据行 `createdAt` 计算的 55.4 秒发生在事务提交前，应予纠正。它也不是浏览器首次可见时间：没有关联 `result_visible` 证据，游客还需轮询发现、授权读取、下载和解码。

| 模型完成后的顺序区间                                                         | 三笔平均 |
| ---------------------------------------------------------------------------- | -------- |
| 记录完成 → `verification_started`（收尾启动、输出登记、审核接续）            | 6.820 秒 |
| 审核开始 → `submission_recorded`（领取、原图读取与审核图准备、提交身份保存） | 5.567 秒 |
| 提交身份保存 → 首次查询得 PENDING（POST、绑定、查询）                        | 3.206 秒 |
| 首次 PENDING → 查询到 ALLOW（PENDING 保存、轮询等待、再次领取和查询）        | 8.792 秒 |
| ALLOW → `verdict_transaction_completed`                                      | 3.259 秒 |

这里只发生一项输出审核任务，处理中查询不是重新提交审核。第二、三笔的素材回调时间字段为空，日志证明其通过查询取得 ALLOW；这不能单独证明供应商没有发送回调。最后一笔首次 PENDING 保存耗时 2.108 秒，保存后至下一审核执行开始 4.774 秒，再次领取及查询准备 1.432 秒，GET 450 ms，最后审核提交事务 3.197 秒。

这 27.6 秒不能称为 SeeAPI 纯审核耗时：至少开始提交前约 12.4 秒与获取 ALLOW 后约 3.3 秒属于本站链路。POST/绑定和轮询区间也混有本站数据库及调度开销。归档分别于 19:59:09.852、21:00:43.296、03:00:28.728 完成，确实没有作为 READY 的门槛。

本批扫描隔离修复解决游客生成前及素材移交的扫描依赖；**并不等于已经优化上述全部 27.6 秒**。后续优化应单独测量并减少收尾接续、领取/提交事务的串行往返及已受理审核的发现延迟，保留审核结论、来源身份和授权状态的原子提交。不能删除这些校验或把事务内写入时间当成可展示时刻。

## 本地验证

通过：API 7 文件 88 项、Jobs 5 文件 138 项、Workflow 3 文件 69 项、支付 webhook 5 项；PostgreSQL Outbox/素材复制 98 项、供应商原图与接续 28 项。覆盖事务失败不唤醒、游客原身份接续、清理分区、清理占满时客户控制任务仍可运行、原图审核后可用及账本保护。相关工作区类型检查、改动文件格式/静态检查、`git diff --check`、Worker dry-run 构建通过。

实际本地 workerd/Workflow 无全局 Outbox 扫描检查通过：`.cache/scan-isolation-20261115/runtime-v8/new-busy-delayed-rpc.json`，一笔任务成功、错误列表为空，浏览器解码可见、供应商提交次数和结算检查通过。真实维护恢复任务等待另一条数据库行锁 3.5 秒并成功提交，主任务仍独立推进。外部供应商为固定延时夹具，图片通过真实本地 Images 转换；这是一个场景的功能证据，不是线上耗时或八场景旧版对比认证。

本地驱动修复了过期的机器专属哈希路径、缺失 Images binding、旧 SeeAPI 图片请求夹具和不能被真实解码器解码的历史 PNG。中途失败记录保留在同目录 `scanless*.log`，不能作为通过证据。曾验证旧接收兼容的 v6 结果已被用户要求后的 v8 结果替代；当前维护占用夹具使用真正的 `media-recover-finalizing-generations`，不再把取消任务发送到旧维护通道。

完整浏览器回归未全绿：主套件 71 通过、5 失败（头像 PUT、移动端返回参数、积分不足及两项免费模型升级断言）；游客补跑 40 通过、3 失败、3 跳过（游客首次入口按钮、桌面工具导航、开发资源 originality 检查）。免费积分断言仍期待 10，实际为 0；游客入口未进入提交阶段。失败日志分别为 `e2e-v2.log` 与 `e2e-guest.log`。未将这些失败冒充通过，也未为通过检查而修改权益、素材权限或降低审核要求；因此本轮不构成完整发布验收。

所有外部供应商使用本地夹具；生产只读查询，不重放客户生成。
