# 后台扫描与客户等待审计

日期：2026-11-15。范围：只读核对生产 PostgreSQL、Cloudflare 部署和日志，并追踪代码；本次仅新增本文，不修改运行逻辑、不操作客户任务、不提交或部署。本文中的时间为 UTC，展示北京时间时另标注。

## 结论

后台扫描负责找回已提交但未执行的工作、恢复超时租约、补账和清理。业务状态由 PostgreSQL 决定，扫描不是业务状态的唯一执行入口，也不是客户并发人数计数器。

当前存在可核实的体验问题：正常游客生成和登录后的素材移交仍依赖扫描；维护通道又混合客户操作与反复延后的清理。生产日志已经证明旧删除检查在同批次挡住了游客准入。正常注册用户图片提交、普通审核回调和原生视频则已有即时推进路径，不能笼统说全站所有操作都在等一分钟。

## 生产版本与计时边界

- 网站：`ezimageai-site-production`，版本 `ff6517a3-53e0-4f39-bab5-c027012a9789`，100%，部署于 2026-11-14 18:10:04.944Z。
- Jobs：`ezpic-workflows-workers-production`，版本 `fe4a3a19-bc6a-4652-b661-dc81438deac1`，100%，部署于 2026-11-14 18:04:40.529Z。
- 两者发布 SHA：`3fc8b3efff3b3562f41064419d6e66e16e1bd724`。审计期间重新核对，未变化。
- 线上 Cron 为 `* * * * *`。每分钟触发不代表每分钟内能执行完。
- `Outbox.processedAt - createdAt` 包含处理、等待、重试和回执补记，不能直接当成客户排队时间。
- `availableAt` 会被延后，不能拿当前值代替初始到期时间。`dispatchEligibleAt` 会被游客准入覆盖，不能据此声称有固定的“计划排队”。
- 本文未测浏览器完整渲染，也不把供应商完成的本地发现时间当成供应商内部实际完成时间。

## 扫描负责的内容

| 触发频率         | 工作                                                                                                    | 对客户的作用                               |
| ---------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 每分钟           | 素材复制恢复、Outbox 投递、生成收尾恢复、审核/原图归档恢复、支付处理租约恢复；本轮末尾再投递一次 Outbox | 找回丢失唤醒和中断的操作                   |
| 每 5 分钟        | 生成对账、游客期限与风险状态检查                                                                        | 核实异常供应商任务、释放符合条件的游客资源 |
| 每 15 分钟       | 过期草稿、上传会话清理                                                                                  | 清理失效上传及其占用                       |
| 每小时第 5 分钟  | 到期且符合条件的付费账期积分发放                                                                        | 补发已到开始时间的待发账期权益             |
| 每小时第 15 分钟 | 订阅对账及其延续任务                                                                                    | 修复漏通知、订阅及支付状态差异             |
| 每分钟，独立路径 | 原生视频执行与资源恢复，各自有界分页                                                                    | 不占用旧的图片维护通道                     |

Outbox 还承载：游客准入、图片提交/收尾/结算、上传审核、供应商通知、支付到账、取消订阅及退款终止、取消生成、素材复制、图片归档、结果通知和物理清理。它是事务内的持久工作记录，不等于必须全局扫描。

代码入口：`apps/workflows/src/workers.ts`、`apps/workflows/src/video-runtime.ts`、`packages/jobs/src/orchestration/registry.ts` 的 `maintenanceTasksAt`、`apps/workflows/src/orchestrator.ts` 的 `runMaintenance`，事件映射在 `packages/jobs/src/handlers/deliver-outbox-event.ts`。

## P1：客户操作与旧清理争用同一个维护执行通道

`worker-executors.ts` 将 Outbox、游客准入、支付处理、取消订阅和清理归入 `jobs-maintenance`，该通道 `maxActive: 1`。通用 Outbox 一次最多领取 50 条，按到期时间选取，不区分客户正在等待的操作和后台清理；`dispatch-outbox.ts` 逐条等待投递。清理在持有父任务执行名额时内联执行。

2026-11-15 08:06 左右的生产快照：约 970 条 PENDING 图片删除、51 条 PENDING 上传清理，还有少量 LEASED 删除。另有 381 条删除 DEAD_LETTER；后者不参与正常领取，不能把它们都算成正在占用执行通道。

删除暂停分支会先执行数据库身份/授权检查，再通过 `ImageDeletionPausedError` 延后 1 小时，保留原事件和存储占用。保留原图的策略正确，但大量已暂停的事件不断进入公共维护通道，产生无效竞争。

同批次生产证据：

- Workflow：`job-da98e663294bbf432860d4306aa3f1fbd7fc7f89f04045f16e44eb1c5dd66bd1`。
- 02:57:51.767：`media-deliver-outbox` 开始。
- 02:57:51.959 至 02:58:29.662：先后启动 **15 条**旧 `media-delete-object`。
- 02:58:32.149：才开始游客 `cmwh8vbav000gpsp7dytxkc27` 的准入；与同批扫描开始相隔 **40.382 秒**。
- 此后又执行 5 条旧删除；本次 Outbox 总执行 **56.647 秒**。
- 同一 Workflow 在进入该扫描前已有多次 `phase=busy, maximum=1, active=1, capacityWaitMs=25000`。
- 扫描结束于 02:58:48.414，下一项收尾恢复直到 03:03:45.915 才开始，中间有 11 次每次 25 秒的 busy 记录；恢复处理本身仅 **202 ms**。

这证明维护任务之间存在实际竞争，不是由“有几个客户同时生成”推断的容量不足。不能把上述全部等待归给 Cloudflare Cron 自身，也不能因此放开图片删除。

修复方向：客户工作使用精确事件即时唤醒；资源清理独立领取、独立预算；暂停删除进入可恢复的低频/休眠处理，而不反复占用客户通道。保持显式删除授权、暂存清理、额度和未知写入保护。

## P1：游客正常生成没有即时入口，准入后的继续执行通知被丢弃

`submit-guest-generation.ts` 只持久化准入结果，没有即时唤醒。`executor.ts` 的内联 Outbox 子任务只转交 `media-process-provider-webhook` 的 continuation，忽略了 `media-admit-guest-generation` 已返回的后续事件。

上一轮核实的发布后 3 笔成功游客 H3 1K：创建到供应商提交平均 127.092 秒，全程到终态平均 190.704 秒。输入素材在创建任务前已通过审核。最新一笔准入后，已提交的生成事件约 64 秒后才开始执行。

修复方向：事务提交后立即唤醒同一持久准入身份；准入成功后转交确切的后续事件。保留试用资格、资金保留、幂等和不确定受理保护。

## P1：登录后的素材移交还存在两个扫描依赖

`claim-generation-draft.ts` / `complete-guest-link-intent.ts` 完成事务后没有唤醒素材复制。`createAccountInputCopyInTransaction` 只写 `ACCOUNT_INPUT_COPY_REQUESTED`。复制完成若无法继承有效审核，数据库写入 `MEDIA_ASSET_VERIFY`，但 `media-copy-account-input` 没有返回审核 continuation，也不在 `shouldDeliverNextStage` 的推进名单。

生产样本 `b5d2474d-8795-4a14-9a4f-32cc841d8f40`：

| 事件                 | UTC 时间                |
| -------------------- | ----------------------- |
| 复制意图建立         | 2026-11-14 16:54:05.832 |
| 第一条审核意图建立   | 16:55:39.378            |
| 目标图片 finalizedAt | 16:55:40.790            |
| SeeAPI 提交          | 16:57:24.573            |
| APPROVED 证据记录    | 16:57:40.336            |

复制完成到审核提交相隔 **103.783 秒**；复制意图到审核证据相隔 **214.504 秒**。前者包含调度与审核提交准备，不能全算成供应商审核；后者也不是纯排队。`RegisteredEditor.tsx` 在 preparation 未 READY 时显示 `AccountInputPreparation`，因此直接影响登录后继续编辑。该样本发生在最新发布之前，但对应复制/推进代码与当前发布版本一致。

修复方向：领取草稿后立即唤醒复制；复制事务返回审核事件，直接接续同一审核，恢复扫描只处理异常。

## P1/P2：支付到账、取消和部分权益处理依赖维护扫描

- 支付 Webhook（`packages/payments/provider/index.ts`、Stripe 入口）及 PayPal 积分包/Image Pass capture：认证持久化 `payment_event` + Outbox 后返回，没有立即唤醒处理。到账处理又属于维护通道。
- PayPal/Waffo 取消订阅：记录取消请求和 Outbox，等扫描实际向供应商确认；Stripe 的直接取消分支不同。
- 提交前取消生成：接口立即写 CANCELED，但释放预留积分的 `GENERATION_SETTLE` 只入 Outbox。已受理且确实支持取消的供应商任务也只排入取消事件。不能对未支持取消或未知受理任务强行取消。
- 已到期的待发付费账期：定时补发每小时触发一次；属于较粗的权益到账时点，需要和即时支付处理区分。
- 用户删除图片：访问撤销与物理清理分离；后续清理和存储额度释放可能等待扫描，这种异步语义需要明确反馈。

最近 30 天生产 Outbox 中未找到 PAYMENT_EVENT_RECEIVED、SUBSCRIPTION_CANCELLATION_REQUESTED 或 GENERATION_CANCEL_REQUESTED 样本。本节是已部署代码确认的等待路径，**没有对应客户实际到账/取消延迟测量**。

修复方向：合法事件持久化后立即唤醒同一处理身份；支付/取消等客户操作与清理分离，保留不可变账本、租约、所有权和供应商确认。

## P2：结果通知快速发布不稳定，但前端仍有轮询保护

发布后 3 笔游客结果通知的 created-to-ACK 分别为 **38.850 / 71.018 / 65.318 秒**，均由 Outbox 后续处理。这不证明首次通知送达时刻，也不证明客户多等同样时长：快速发布成功但 ACK 丢失也可能造成回执晚记。

`publish.ts` 快速发布预算 250 ms，异常返回 false，保留 Outbox，但没有持久区分超时、Hub 失败或 ACK 失败，难以从现有记录诊断快路径为何未完成。

注册用户活跃任务仍独立每 2 秒读授权状态；游客每 2.5 秒轮询，未订阅注册用户的结果 WebSocket。因此这些游客任务不能把通知 ACK 延迟直接计入结果可见延迟。

修复方向：记录快速发布和 ACK 的阶段结果，检查实际传输/数据库生命周期，保持轮询兜底；不要因 WebSocket 健康而取消授权状态读取。

## 正常情况下已有即时路径的内容

- 注册用户创建图片：事务返回事件后，`create-generation.ts` 立即投递精确事件；临时参考图上传也立即启动审核。
- SeeAPI / Kie 正常回调：持久保存唤醒证据后唤醒所属阶段，并保留原 Workflow 的查询；扫描用于失效/漏通知恢复。
- 图片生成后的正常收尾与结算：有精确 continuation；不能把 Outbox 完成时间当成等待扫描的证据。
- 合格供应商原图交付：审核通过即可按现行权限读取，独立归档完成不是通用展示门槛。
- 原生视频：每分钟恢复单独执行，与旧维护通道分离；其正常 Workflow 的供应商/审核轮询是另一个机制。

## 建议实施顺序与验收

1. 先隔离暂停清理与客户工作，并消除游客启动/准入接续断点。
2. 补齐素材复制、审核接续和支付/取消的即时唤醒。
3. 恢复扫描分为有界独立工作，避免一分钟新触发不断排在旧批次后；补齐到期、首次执行、提交、完成证据、通知及页面发现的分段指标。
4. 回归需覆盖：无 Cron 仍能完成正常路径；大量暂停删除不拖慢客户事件；重复/丢失唤醒不重复提交、发放或扣费；恢复仍能处理漏唤醒；图片保留与审核门槛不变。
