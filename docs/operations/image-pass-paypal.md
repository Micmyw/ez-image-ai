# PayPal three-image purchase

The offer `image-pass-3`, version `2026-10-19.1`, costs exactly USD 1.00 and grants three successful single-image outputs across the 29 image SKUs frozen in its offer snapshot. It grants no general credits, subscription permissions, video quota, or recurring payment. A user can purchase again using a fresh checkout idempotency key. An existing pending command reuses its existing order.

The authenticated checkout is always owned by `user.id`; an active organization does not receive this offer. Creation accepts PayPal, an idempotency key and checkout attribution. Amount, currency, merchant SKU and offer snapshot are server-owned. The dedicated PayPal Orders SKU is `EZIMAGE-IMAGE-PASS-3-USD-1-20261019`; this is a merchant line-item identifier, not a remotely provisioned subscription plan.

Creation requires an active exact-match BillingPlan: provider `paypal`, productKind `IMAGE_PASS`, name `image-pass-3`, priceMicros `1000000`, currency `USD`, creditsPerPeriod `0`, and metadata.imagePassOfferSnapshot equal to `getImagePassOfferSnapshot()`. Checkout intents retain their own frozen snapshot. Changes to the offer or SKU list require a new reviewed version, not mutation of historical purchase terms.

The return page uses owner-scoped state and capture procedures. A URL token, approval or browser return cannot grant units. Capture verifies the trusted order/intent and final completed capture, amount USD 1.00, then persists the normalized payment event through the existing verified-event ingestion path. The event processor grants in a transaction through the dedicated image-pass ledger. Capture response and signed webhook duplicates bind the same order/capture/intent and cannot grant twice. If PayPal reports `ORDER_ALREADY_CAPTURED`, the adapter retrieves that exact order with server authentication and validates the completed representation.

Verified capture refunds, capture reversals and `CUSTOMER.DISPUTE.CREATED` events route to the bound image-pass purchase before ordinary credit reducers. A partial refund or dispute freezes all unspent units, while reservations with uncertain provider outcomes remain held until the existing terminal finalization path resolves them. This code does not unfreeze units based on dispute resolution or create normal-credit debt. A dispute must contain exactly one seller transaction binding; ambiguous facts require review.

Grant and adjustment paths share `image-pass-payment:paypal:<capture-id>` advisory locks. Consumption and revocation additionally share the owner lock, with payment before owner. Earlier adjustments missing payment correlation remain durably failed; fulfillment requeues exact-capture adjustments through the outbox. The processor also checks again after persisting a missing-correlation failure, closing the race where fulfillment committed between the first lookup and failure persistence. Requeue uses an event-specific dedupe key.

Before a separately approved rollout, apply the reviewed migration and provision its exact BillingPlan, regenerate the official locked Prisma client, and run the full checks. Verify existing PayPal live configuration and merchant Orders/capture permissions without displaying credentials: `PAYPAL_ENVIRONMENT`, `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID`, `BILLING_ENABLED`, and the application return origin. Verify the merchant webhook subscription includes `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.CAPTURE.REVERSED`, and `CUSTOMER.DISPUTE.CREATED`, and that the existing payment-event/outbox workers run. No new payment secret or remote PayPal product is required by this implementation. Live account settings and real transactions have not been inspected or exercised by the local tests.

The isolated SQL integration tests target only `127.0.0.1:55439/image_pass_test` locally or the dedicated `55441/image_pass_test` CI service, use unique fixtures and do not truncate shared data. They run real entitlement SQL with a PostgreSQL transport; they do not establish that official generated Prisma integration or real PayPal payments passed. The official Prisma download remains blocked by the platform's `binaries.prisma.sh` 403 policy; do not bypass TLS, checksum validation or that network policy.

PayPal protocol references: [capture/refund/dispute webhook events](https://developer.paypal.com/api/rest/webhooks/event-names/) and [official Disputes schema](https://developer.paypal.com/api/customer-disputes/v1/schema.json), including `disputed_transactions[].seller_transaction_id` and `dispute_amount`.

## Candidate migration, provisioning and release boundary

`packages/database/prisma/migrations/20261019010000_image_pass/migration.sql` is a prepared additive delta, not a production execution record. It adds the independent grant/unit/reservation/immutable-ledger/adjustment tables, an IMAGE_PASS product kind, a server checkout snapshot and an explicit job funding source. It changes the job credits check to require positive ordinary credits or exactly zero credits for an image pass, and preserves ordinary credit-reservation exclusivity with a binding trigger. All paid identities are immutable and every committed pass grant requires exactly three numbered units. The migration uses one PostgreSQL transaction; the new enum value is only compared as text inside that transaction and is first used for inserted billing rows after commit.

The five new tables enable RLS and revoke direct access from PUBLIC and existing Supabase API roles. The existing server-only `ezpic_app` role receives explicit DML and its own policy when present; Better Auth identities are not mapped to Supabase browser policies. Trigger functions keep invoker privileges, a fixed `pg_catalog,public,pg_temp` search path and no PUBLIC execute grant. This matches the existing private operational-table pattern and [Supabase's grants/RLS guidance](https://supabase.com/docs/guides/api/securing-your-api). It does not change existing table or schema privileges.

`docs/operations/image-pass-paypal-provision.sql` is a separately reviewable, idempotent provision for the fixed one-time PayPal merchant SKU. It inserts only the exact USD 1 / three-unit / 29-current-image-SKU offer and refuses an existing row with different pricing or metadata. It creates no subscription and calls no PayPal API. Both files are for an explicitly approved target. Do not blindly deploy the repository's full migration history to the populated production database, or fabricate `_prisma_migrations` history.

Release requires independent review and complete official-client CI, reviewed production migration/provision authorization, then compatible jobs consumers before website producers/UI. Keep the IMAGE_PASS BillingPlan completely absent until both compatible deployments are verified, including absence of any inactive placeholder that old generated enum readers could encounter. Run the active-row provision last. Current production binding name/type metadata establishes only that PayPal and billing configuration exists. Secret values were not read; Live runtime mode, credential validity and merchant ability to accept a payment remain **UNVERIFIED**, and the new offer billing row is not yet provisioned. No real payment or generation acceptance test was run. Publishing the banner does not certify a working live checkout.

Rollback should first stop new offer checkouts by deactivating only the exact IMAGE_PASS billing-plan row through the approved process, retain all grants/units/ledger/payment facts, and keep compatible jobs consumers running until accepted pass jobs have a known terminal settlement. An already verified paid capture remains eligible for idempotent fulfillment even after checkout intake stops. Do not drop the tables, remove the enum value, restore the old positive-credit-only job CHECK, delete the offer history, or deploy an old consumer while a pass reservation is active. A website rollback cannot erase paid entitlements; restore a compatible reader/consumer to make them usable again.

These local artifacts and fixture results do not authorize production DDL, provisioning, remote model calls, payment capture, merging or deployment. Root coordinates the remaining approvals and release.
