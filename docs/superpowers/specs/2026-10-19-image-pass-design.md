# PayPal USD 1 image pass

Authorized scope: repeatable one-time PayPal purchase of three successful single image outputs, including every current image SKU and 4K. No subscription. Existing credit products, subscriptions, prices, free storage/concurrency/input restrictions, moderation and provider safety budgets retain their current meaning. No real payment or generation acceptance call. Production migration, push, PR and deployment require coordination after independent review; this branch only prepares reviewable artifacts.

Use a separate image-pass grant, three individually numbered units, per-job reservations, immutable unit ledger and verified refund/dispute adjustment. Never grant 75 ordinary credits. PayPal capture fulfillment validates exactly USD 1 and the server checkout's versioned offer snapshot, then atomically creates one purchase and exactly three units. Provider capture/order and checkout bindings are unique; repeated events, return/capture recovery and duplicate fulfillment cannot mint more units. A pending or unverified return grants nothing.

Generation chooses explicit `fundingSource: CREDITS | IMAGE_PASS`; omitted means existing CREDITS behavior. Freeze the selected funding in the moderated quote/fingerprint. No fallback when the selected balance is insufficient. IMAGE_PASS authorizes all 29 current image SKUs from the server offer snapshot, including 4K, without granting video or subscription status. Each quote and server admission requires one output. Admission uses the existing current owner/asset/moderation/rate/storage/concurrency/provider budget checks, locks a single available unit under its owner, binds it to one job, and creates no ordinary credit reservation. Pass jobs record zero credits reserved and a distinct funding source.

Only exactly one privately stored, currently moderated, usable output consumes a unit. A confirmed terminal failure with no usable output releases it once; content moderation blocks release it under this pass's successful-output promise, without changing ordinary-credit moderation billing. Unknown submission/provider acceptance, manual reconciliation and incomplete moderation retain the same reservation. A late real success consumes that reservation once. Transfer/finalization retries, polling, repeated clicks and callbacks never reserve twice. Cancellation follows the existing provider-terminal safety boundary, not the UI request lifetime.

A verified positive refund/dispute freezes the paid grant and revokes its available units; it never transfers value into ordinary credits/debt. Reserved units keep their job binding until a known terminal outcome. Such a job's success consumes the held unit; failure moves it to revoked, not spendable. Consumed units remain in history. The implementation does not initiate a refund or decide a monetary partial-refund policy. No expiry is introduced without user instruction.
